# 📘 AI 시대의 프로젝트 관리 강의 정리

## 1. 강의 개요

### ✅ 프로젝트를 바라보는 컨셉

* IT 개발 프로젝트를 처음 수행하며 프로젝트 계획 및 관리 경험이 부족한 사람들을 위한 강의
* IT 현장의 선배들이 실제로 어떻게 계획하고 관리하는지 이해
* SSAFY 프로젝트 환경과 비교하여, **우리 팀에 맞는 관리 방법**을 찾는 것이 핵심

### ✅ 갈등을 바라보는 컨셉

* IT 개발 프로젝트에서도 **갈등은 필연적**
* 갈등이나 문제는 없을 수 없으며, 생기는 것이 오히려 **정상적인 현상**
* 갈등이 발생했을 때 누가 나쁘다는 인식이 아닌, **자연스러운 현상으로 이해**
* 선배들의 갈등 대응 방식 학습 → SSAFY 프로젝트에 맞춰 **효과적으로 대응**하는 법 준비

---

## 2. 프로젝트 기본 관리 방안

### ✅ IT 현장에서 프로젝트를 관리하는 방법

| 구분                    | 설명                               |
| --------------------- | -------------------------------- |
| **계획 및 역할 분배**        | 프로젝트 진행 계획 수립 후 구성원 역할 분배        |
| **역할에 따른 수행 및 진척 관리** | 각자 맡은 역할에 맞게 업무 수행하고 진척도 관리      |
| **문제 및 갈등 관리**        | 프로젝트 중 발생하는 갈등이나 문제를 PM이 조정하고 해결 |

---

### ✅ IT 프로젝트 관리의 핵심: **갈등 관리**

* 프로젝트에서 가장 중요한 관리 개념 중 하나는 **갈등 관리**
* 프로젝트 수행 중 문제를 효과적으로 관리하기 위한 **3가지 장치** 존재

#### 1) 방법

* 업무 분해
* 역할 분배 & 일정 계획
* 보고 체계
* 일정 및 변경 관리

#### 2) 권한

* PM(팀장), PL(파트장) 등 역할별 책임 명확히
* SSAFY에서는 **팀장을 PM으로 간주**해 프로젝트 관리

#### 3) 규칙

* 반복적인 프로젝트 경험으로 만들어진 규칙을 통해 **문제 예방**
* 예측 가능한 문제는 규칙으로 최소화

---

## 3. 방법 관점 관리

### ✅ 프로젝트를 방법 중심으로 관리

> 업무 방법을 통해 운영하고, 문제 상황을 최소화

#### 주요 항목

* **업무 분해**: 전체 업무를 세부적으로 쪼개어 관리
* **역할 분배 및 일정 계획**: 누가 언제까지 무엇을 할지
* **보고**: 정기적으로 상황 공유
* **일정 및 변경 관리**: 변경사항 반영, 일정 재조정 등

## ✅ 방법 관점 관리

### 📌 역할 분배 & 일정 계획

* 업무 분해 후 프로젝트 멤버에게 역할 및 일정 분배
* PM과 PL이 1차 업무 분배 → 구성원 전체가 리뷰
* 어려움, 과업 과다/부족, 개인 상황 등을 고려하여 조정

> 📌 "업무 분배가 자연스럽게 이뤄지면, 대부분의 구성원이 '잘못됐다'고 느끼지 않음"

---

### 📌 보고

* **정기적인 주간/월간 보고**로 진척 관리
* 구성원이 **PM에게 능동적으로 보고**하는 구조 권장
* PM은 보고를 통해 개발 진척, 문제, 갈등 등 이슈 파악

> 🔁 PM 1\:N 확인 vs 구성원 1:1 보고 → 후자가 정확도 ↑

---

### 📌 일정 및 변경 관리

* 문제 발생 후가 아닌 **사전 공유** 필요
* 개인의 주관적 판단이 일정 지연의 원인이 될 수 있음
  → `"나는 감당할 수 있을 줄 알았음"`이라는 오판 주의
* 진척된 사실 공유 → PM이 판단하고 대응
* 빠르게 해결하는 사람에게 책임/성과 부여

---

### 📌 WBS 관리 (Work Breakdown Structure)

* WBS: **방법 관점의 결과를 정리하고 통합 관리**하는 문서

#### WBS 구성 항목

* 사업 정보: 프로젝트 기간, 기준일 등
* 업무 분해: Depth 별 단계, 업무 항목
* 일정 계획: 시작일, 완료일, 실제 일정
* 담당자, 산출물, 진척률 등

> ✅ WBS로 업무/일정/산출물/담당자/위험도까지 한눈에 관리 가능

---

## ✅ 권한 관점 관리

### 📌 수직적 권한 기반 관리

* PM이 **의사결정, 조정, 관리 권한** 보유
* 부여된 권한에 따라 **최종 책임** 존재
* PL은 PM을 **지원하는 역할**
* 구성원은 PM의 관리 하에 **수행자 역할**

### 📌 수직 vs 수평 구조의 오해

* `[수직 = 불합리]`, `[수평 = 합리]`는 **오해**
* 실제로는 수평 구조에서 **갈등이 더 많이 발생**
* 핵심은 **명확한 권한에 기반한 효율적 관리**

---

## ✅ 규칙 관점 관리

### 📌 반복되는 문제에 대한 조직의 대응

* 문제는 반복적으로 발생하기 때문에 **예측 가능한 상황**은 규칙으로 정리
* **경험 기반**으로 규정, 가이드, 문화 형성

#### 규칙의 3가지 유형

| 유형  | 설명                   | 예시                   |
| --- | -------------------- | -------------------- |
| 규정  | 불합리한 행위에 대한 대응       | 무단 결근 시 대처 규정        |
| 가이드 | 업무 중 발생하는 갈등 해결 가이드  | 퍼블리싱/프론트엔드 개발 범위 명확화 |
| 문화  | 조직의 공유 가치에 기반한 해결 방식 | 갈등 시 \[OO]의 중재로 조정   |

## ✅ 일반 IT vs 단기 프로젝트 조직 비교

| 항목     | 일반 IT 조직 | 단기 프로젝트 조직 |
| ------ | -------- | ---------- |
| 관리 경험  | 있음       | 부족         |
| 강제성    | 강함       | 약함         |
| 조직 관계  | 수직       | 수평         |
| 대응 규칙  | 존재       | 부족         |
| 평가 영향력 | 강함       | 약함         |

> 📌 SSAFY 프로젝트와 같은 단기 조직에서는 **명확한 기준과 권한 정립이 더 중요함**

## 5. 프로젝트 관리 3요소

### 🔹 방법(Method)

* 업무 분해 (WBS)
* 역할 분배 / 일정 수립
* 주간 보고, 이슈 공유
* 일정 변경 시 조율

### 🔹 권한(Authority)

* PM(팀장): 전반적 관리 및 의사결정
* PL(파트장): 세부 기술 관리
* 구성원: 역할 수행자

### 🔹 규칙(Rule)

* 규정: 불합리 방지용 룰
* 가이드: 갈등/경계 설정
* 문화: 협업 분위기 조성

## 6. WBS(Work Breakdown Structure)

| Depth | 업무 항목                        |
| ----- | ---------------------------- |
| 1차    | 분석 / 설계 / 구현 / 테스트 / 전개 / 오픈 |
| 2차    | 요구사항 분석, DB 설계, 프론트 구현 등     |
| 3차    | 로그인 화면 구현, 장비 예약 API 등       |

**→ 일정, 담당자, 진척률까지 함께 작성**

## ✅ 커뮤니케이션 방식 비교

| 구분            | 설명                            |
| ------------- | ----------------------------- |
| PM → 팀원 확인 방식 | 1\:N 방식으로 비효율 발생 가능, 빠짐/오해 가능 |
| 팀원 → PM 보고 방식 | 1:1 보고 → 정확도 높고 **책임 명확화**    |
| 정기보고 vs 수시보고  | 정기보고는 기본, 이슈는 **수시 보고**로 병행   |

> ⚠️ 주의: ‘상황 공유’를 ‘해결’로 착각하지 말기

## ✅ 일정 공유 & 사전 대응의 중요성

* 개인적 판단으로 \*\*‘될 거라고 생각’\*\*하지 말기
* 사소한 문제라도 **초기에 공유** → 일정 조정 가능
* **문제 발생 전**에 알려야 **팀 전체 일정 보호 가능**
* 해결자에게 책임보다 **성과 인정을 우선**하기

## ✅ 프로젝트 상황 판단의 시야

| 시야    | 설명                  |
| ----- | ------------------- |
| 개인 시야 | 내 업무 상황만 고려         |
| PM 시야 | 전체 일정, 타 업무 연계까지 고려 |
| 팀 시야  | 팀 전체 일정 및 영향도 기반 판단 |

> 👀 "내가 지금 늦으면 어디에 어떤 영향을 주는가?"

## ✅ 갈등과 협업의 핵심

* 문제는 언제든 발생할 수 있음 → **갈등은 '자연스러운 것'**
* 문제 자체보다 **해결 태도와 대응 방식**이 더 중요
* 갈등 시 책임전가보다 **공유 → 협의 → 조정**이 핵심
