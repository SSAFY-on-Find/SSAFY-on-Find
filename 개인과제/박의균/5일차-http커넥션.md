### ✅ @Entity와 @Transactional을 이용한 dirtyChecking을 안쓰는 이유는?

클래스에 @Entity를 붙이고, 서비스레이어에 @Transactional을 붙이면 변경 감지가 자동으로 일어나면서 편한데 왜 도메인과 엔티티를 분리하고, 서비스 레이어가 아닌 Repository에 @Transactional을 붙이면서 불필요한 일들을 해야 되는가?

## ✔️ 답변

### ✅ Post 도메인에 객체를 저장했다고 생각해보자.

```java
@Entity
public class Post{
		@Id
		@GeneratedValue
		private final Long id;
		
		//...
}
```

### ✅ 장점 1. 엔티티를 분리하면 서비스와 도메인의 코드를 바꾸지 않아도 됨

- DB 관련 로직을 추가하거나 변경해도 서비스 계층 코드를 **1줄도** 수정하지 않았다.
- 비즈니스 로직과 영속성 로직이 분리되어 **관심사의 분리(SoC)**를 완벽히 지킨다.

**→ 엔티티를 분리하지 않았을 때, DB로직을 수정하면 서비스 레이어도 영향을 받는다는 것은 큰 문제다!**

### ✅ 장점 2. 동시성 높은 ‘좋아요’ 처리에 레포지토리가 더 유리

- 레포지토리 레벨에서 **원자적(atomic) 증가** 쿼리(`@Modifying UPDATE`)를 실행하면
    
    동시 요청 간 **경합(race condition)** 없이 안전하게 카운트를 올린다.
    
- `updatePostLikeCount` 같은 JPQL 쿼리는 **SELECT 없이** 바로 `UPDATE`하므로
    
    불필요한 조회·쓰기 오버헤드를 모두 감소시킨다.
    

### ✅ 장점 3. 도메인 모델의 순수성(purity) 보장

- `@Entity` 애노테이션과 영속성 API를 **도메인 객체에 섞지 않는다**!!!
- 도메인 로직은 순수 자바 객체(POJO)로 유지되어,
    
    테스트·재사용·리팩토링이 훨씬 간편해진다.
    

### ✅ 장점 4. 명시적 트랜잭션 경계 설정으로 성능·일관성 제어

- 서비스 전체를 하나의 트랜잭션으로 묶으면 **오래 걸리는 작업**까지 락을 유지한다.
- 레포지토리 단위로 트랜잭션을 분리하면 **DB 락 시간 최소화**와 **격리 수준(isolation)** 조정이 용이해진다.

### ✅ 장점 5. 변경 감지(dirty checking)의 부작용 최소화

- JPA의 자동 플러시 타이밍은 **예측하기 어려워**, 의도치 않은 `UPDATE` 쿼리가 발생할 수 있다.
- 단일 필드 변경에도 엔티티 전체를 스캔·비교하므로 퍼포먼스와 네트워크 부하가 상승할 수 있다.
